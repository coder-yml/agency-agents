# 🚨 Runbook：事件响应

> **模式**：NEXUS-Micro | **持续时间**：数分钟到数小时 | **代理**：3-8

---

## 场景

生产环境中出了问题。用户受到影响。响应速度很重要，但做对更重要。此 runbook 涵盖从检测到事后复盘的全过程。

## 严重程度分类

| 级别 | 定义 | 示例 | 响应时间 |
|-------|-----------|----------|--------------|
| **P0 — 严重** | 服务完全中断、数据丢失、安全漏洞 | 数据库损坏、DDoS 攻击、认证系统故障 | 立即（全员集结） |
| **P1 — 高** | 重要功能损坏、显著的性能退化 | 支付处理中断、50%+ 错误率、10 倍延迟 | < 1 小时 |
| **P2 — 中** | 次要功能损坏、有临时解决方案 | 搜索不可用、非关键 API 错误 | < 4 小时 |
| **P3 — 低** | 外观问题、轻微不便 | 样式 bug、拼写错误、小 UI 故障 | 下一个冲刺 |

## 按严重程度的响应团队

### P0 — 严重响应团队
| 代理 | 角色 | 行动 |
|-------|------|--------|
| **Infrastructure Maintainer** | 事件指挥官 | 评估范围、协调响应 |
| **DevOps Automator** | 部署/回滚 | 如需要执行回滚 |
| **Backend Architect** | 根因调查 | 诊断系统问题 |
| **Frontend Developer** | UI 端调查 | 诊断客户端问题 |
| **Support Responder** | 用户沟通 | 状态页更新、用户通知 |
| **Executive Summary Generator** | 利益相关方沟通 | 实时执行更新 |

### P1 — 高响应团队
| 代理 | 角色 |
|-------|------|
| **Infrastructure Maintainer** | 事件指挥官 |
| **DevOps Automator** | 部署支持 |
| **相关开发者代理** | 修复实现 |
| **Support Responder** | 用户沟通 |

### P2 — 中响应
| 代理 | 角色 |
|-------|------|
| **相关开发者代理** | 修复实现 |
| **Evidence Collector** | 验证修复 |

### P3 — 低响应
| 代理 | 角色 |
|-------|------|
| **Sprint Prioritizer** | 添加到待办列表 |

## 事件响应序列

### 步骤 1：检测与分类（0-5 分钟）

```
触发器：来自监控的告警 / 用户报告 / 代理检测

Infrastructure Maintainer：
1. 确认告警
2. 评估范围和影响
   - 多少用户受到影响？
   - 哪些服务受影响？
   - 数据是否存在风险？
3. 分类严重程度（P0/P1/P2/P3）
4. 激活相应的响应团队
5. 创建事件频道/线程

输出：事件分类 + 响应团队已激活
```

### 步骤 2：调查（5-30 分钟）

```
并行调查：

Infrastructure Maintainer：
├── 检查系统指标（CPU、内存、网络、磁盘）
├── 审查错误日志
├── 检查最近的部署
└── 验证外部依赖

Backend Architect（如果是 P0/P1）：
├── 检查数据库健康
├── 审查 API 错误率
├── 检查服务通信
└── 识别故障组件

DevOps Automator：
├── 审查最近的部署历史
├── 检查 CI/CD 管道状态
├── 如需要准备回滚
└── 验证基础设施状态

输出：根因已识别（或缩小到组件级别）
```

### 步骤 3：缓解（15-60 分钟）

```
决策树：

如果由最近的部署引起：
  → DevOps Automator：执行回滚
  → Infrastructure Maintainer：验证恢复
  → Evidence Collector：确认修复

如果由基础设施问题引起：
  → Infrastructure Maintainer：扩缩/重启/故障切换
  → DevOps Automator：支持基础设施变更
  → 验证恢复

如果由代码 bug 引起：
  → 相关开发者代理：实现热修复
  → Evidence Collector：验证修复
  → DevOps Automator：部署热修复
  → Infrastructure Maintainer：监控恢复

如果由外部依赖引起：
  → Infrastructure Maintainer：激活回退/缓存
  → Support Responder：向用户沟通
  → 监控外部恢复

全程：
  → Support Responder：每 15 分钟更新状态页
  → Executive Summary Generator：简报利益相关方（仅 P0）
```

### 步骤 4：解决验证（修复后）

```
Evidence Collector：
1. 验证修复是否解决了问题
2. 工作状态的截图证据
3. 确认没有引入新问题

Infrastructure Maintainer：
1. 验证所有指标恢复到正常水平
2. 确认没有级联故障
3. 修复后监控 30 分钟

API Tester（如果与 API 相关）：
1. 对受影响的端点运行回归测试
2. 验证响应时间已恢复正常
3. 确认错误率在基线水平

输出：事件已解决确认
```

### 步骤 5：事后复盘（48 小时内）

```
Workflow Optimizer 主导事后复盘：

1. 时间线重建
   - 问题何时被引入？
   - 何时被检测到？
   - 何时被解决？
   - 用户受影响的总时长

2. 根因分析
   - 什么失败了？
   - 为什么失败？
   - 为什么没有被更早地发现？
   - 5 Whys 分析

3. 影响评估
   - 受影响的用户数
   - 收入影响
   - 声誉影响
   - 数据影响

4. 预防措施
   - 什么样的监控能更早发现？
   - 什么样的测试能防止这个问题？
   - 需要哪些流程变更？
   - 需要哪些基础设施变更？

5. 行动项
   - [行动] → [负责人] → [截止日期]
   - [行动] → [负责人] → [截止日期]
   - [行动] → [负责人] → [截止日期]

输出：事后复盘报告 → Sprint Prioritizer 将预防任务添加到待办列表
```

## 沟通模板

### 状态页更新（Support Responder）
```
[时间戳] — [服务名称] 事件

状态：[调查中 / 已识别 / 监控中 / 已解决]
影响：[用户影响的描述]
当前行动：[我们正在做什么]
下次更新：[下次更新的预期时间]
```

### 执行更新（Executive Summary Generator — 仅 P0）
```
事件简报 — [时间戳]

情况：[服务] 处于 [中断/降级] 状态，影响 [N 个用户/流量百分比]
原因：[已知/调查中] — [如已知，简要描述]
行动：[正在做什么] — 预计恢复时间 [时间估计]
影响：[业务影响 — 收入、用户、声誉]
下次更新：[时间戳]
```

## 升级矩阵

| 条件 | 升级至 | 行动 |
|-----------|------------|--------|
| P0 在 30 分钟内未解决 | Studio Producer | 额外资源、供应商升级 |
| P1 在 2 小时内未解决 | Project Shepherd | 资源重新分配 |
| 疑似数据泄露 | Legal Compliance Checker | 监管通知评估 |
| 用户数据受到影响 | Legal Compliance Checker + Executive Summary Generator | GDPR/CCPA 通知 |
| 收入影响 > $X | Finance Tracker + Studio Producer | 业务影响评估 |
