# 🛡️ 第 4 阶段 Playbook — 质量与加固

> **持续时间**：3-7 天 | **代理**：8 | **关卡守门人**：Reality Checker（唯一权威）

---

## 目标

最终的质量考验。Reality Checker 默认为"需要改进" —— 你必须用压倒性的证据来证明生产就绪。这一阶段存在是因为首次实现通常需要 2-3 个修订周期，而这是健康的表现。

## 前置条件

- [ ] 第 3 阶段质量关卡已通过（所有任务 QA 完成）
- [ ] 第 3 阶段交接包已接收
- [ ] 所有功能已实现并单独验证

## 关键心态

> **Reality Checker 的默认判定是需要改进。**
> 
> 这不是悲观主义 —— 这是现实主义。生产就绪需要：
> - 完整的用户旅程端到端正常工作
> - 跨设备一致性（桌面、平板、移动）
> - 负载下的性能（不仅仅是正常路径）
> - 安全性验证（不仅仅是"我们添加了认证"）
> - 规格合规性（每个需求，不是大多数）
>
> 首次通过的 B/B+ 评级是正常和预期的。

## 代理激活序列

### 步骤 1：证据收集（第 1-2 天，全部并行）

#### 📸 Evidence Collector — 全面视觉证据
```
激活 Evidence Collector 对 [项目] 进行全面的系统证据收集。

所需交付物：
1. 完整截图套件：
   - 桌面（1920x1080）— 每个页面/视图
   - 平板（768x1024）— 每个页面/视图
   - 移动（375x667）— 每个页面/视图
2. 交互证据：
   - 导航流（点击前后的对比）
   - 表单交互（空、已填、已提交、错误状态）
   - 模态框/对话框交互
   - 手风琴/可展开内容
3. 主题证据：
   - 浅色模式 — 所有页面
   - 深色模式 — 所有页面
   - 系统偏好检测
4. 错误状态证据：
   - 404 页面
   - 表单验证错误
   - 网络错误处理
   - 空状态

格式：含 test-results.json 的截图证据包
时间线：2 天
```

#### 🔌 API Tester — 完整 API 回归测试
```
激活 API Tester 对 [项目] 进行完整 API 回归测试。

所需交付物：
1. 端点回归套件：
   - 所有端点已测试（GET、POST、PUT、DELETE）
   - 认证/授权验证
   - 输入验证测试
   - 错误响应验证
2. 集成测试：
   - 跨服务通信
   - 数据库操作验证
   - 外部 API 集成
3. 边缘情况测试：
   - 速率限制行为
   - 大负载处理
   - 并发请求处理
   - 格式错误输入处理

格式：API 测试报告，每个端点含通过/不通过
时间线：2 天
```

#### ⚡ Performance Benchmarker — 负载测试
```
激活 Performance Benchmarker 对 [项目] 进行负载测试。

所需交付物：
1. 在 10 倍预期流量下的负载测试：
   - 响应时间分布（P50、P95、P99）
   - 负载下的吞吐量
   - 负载下的错误率
   - 资源利用率（CPU、内存、网络）
2. Core Web Vitals 测量：
   - LCP（最大内容绘制）< 2.5s
   - FID（首次输入延迟）< 100ms
   - CLS（累计布局偏移）< 0.1
3. 数据库性能：
   - 查询执行时间
   - 连接池利用率
   - 索引有效性
4. 压力测试结果：
   - 崩溃点识别
   - 优雅降级行为
   - 过载后的恢复时间

格式：性能认证报告
时间线：2 天
```

#### ⚖️ Legal Compliance Checker — 最终合规审计
```
激活 Legal Compliance Checker 对 [项目] 进行最终合规审计。

所需交付物：
1. 隐私合规验证：
   - 隐私政策准确性
   - 同意管理功能
   - 数据主体权利实现
   - Cookie 同意实现
2. 安全合规：
   - 数据加密（静态和传输中）
   - 认证安全性
   - 输入净化
   - OWASP Top 10 检查
3. 监管合规：
   - GDPR 要求（如适用）
   - CCPA 要求（如适用）
   - 行业特定要求
4. 无障碍合规：
   - WCAG 2.1 AA 验证
   - 屏幕阅读器兼容性
   - 键盘导航

格式：合规认证报告
时间线：2 天
```

### 步骤 2：分析（第 3-4 天，并行，在步骤 1 之后）

#### 📊 Test Results Analyzer — 质量指标聚合
```
激活 Test Results Analyzer 对 [项目] 进行质量指标聚合。

输入：所有步骤 1 的报告
所需交付物：
1. 聚合质量仪表盘：
   - 总体质量评分
   - 类别细分（视觉、功能、性能、安全、合规）
   - 问题严重程度分布
   - 趋势分析（如有多次测试周期）
2. 问题优先级排序：
   - 严重问题（必须在生产前修复）
   - 高优先级问题（应在生产前修复）
   - 中优先级问题（在下一个冲刺中修复）
   - 低优先级问题（放入待办列表）
3. 风险评估：
   - 生产就绪概率
   - 剩余风险区域
   - 推荐的缓解措施

格式：质量指标仪表盘
时间线：1 天
```

#### 🔄 Workflow Optimizer — 流程效率审查
```
激活 Workflow Optimizer 对 [项目] 进行流程效率审查。

输入：第 3 阶段执行数据 + 步骤 1 的发现
所需交付物：
1. 流程效率分析：
   - 开发↔QA 循环效率（首次通过率、平均重试次数）
   - 瓶颈识别
   - 不同问题类型的解决时间
2. 改进建议：
   - 第 6 阶段运营的流程变更
   - 自动化机会
   - 质量改进建议

格式：优化建议报告
时间线：1 天
```

#### 🏗️ Infrastructure Maintainer — 生产就绪检查
```
激活 Infrastructure Maintainer 对 [项目] 进行生产就绪检查。

所需交付物：
1. 生产环境验证：
   - 所有服务健康并响应
   - 自动扩缩已配置并测试
   - 负载均衡器配置已验证
   - SSL/TLS 证书有效
2. 监控验证：
   - 所有关键指标正在收集
   - 告警规则已配置并测试
   - 仪表盘访问已验证
   - 日志聚合正常工作
3. 灾难恢复验证：
   - 备份系统可操作
   - 恢复程序已记录并测试
   - 故障切换机制已验证
4. 安全验证：
   - 防火墙规则已审查
   - 访问控制已验证
   - 密钥管理已确认
   - 漏洞扫描结果清洁

格式：基础设施就绪报告
时间线：1 天
```

### 步骤 3：最终裁决（第 5-7 天，顺序执行）

#### 🔍 Reality Checker — 最终裁决
```
激活 Reality Checker 对 [项目] 进行最终集成测试。

强制流程 — 不得跳过：

步骤 1：真实性检查命令
- 验证实际构建了什么（用 ls、grep 检查声称的功能）
- 交叉核对声称的功能与规格
- 运行全面的截图捕获
- 审查步骤 1 和步骤 2 的所有证据

步骤 2：QA 交叉验证
- 审查 Evidence Collector 的发现
- 与 API Tester 的结果交叉引用
- 验证 Performance Benchmarker 的数据
- 确认 Legal Compliance Checker 的发现

步骤 3：端到端系统验证
- 测试完整的用户旅程（而非单个功能）
- 在所有设备上验证响应式行为
- 端到端检查交互流程
- 审查实际性能数据

步骤 4：规格真实性检查
- 引用原始规格中的确切文本
- 与实际实现证据进行比较
- 记录规格与现实之间的每个差距
- 没有假设 — 只有证据

判定选项：
- 就绪：压倒性的生产就绪证据（首次通过很罕见）
- 需要改进：具体问题已识别，附修复列表（符合预期）
- 未就绪：需要重新审查第 1/2 阶段的重大架构问题

格式：基于真实性的集成报告
默认：需要改进，除非有相反证据
```

## 质量关卡 — 最终关卡

| # | 标准 | 阈值 | 所需证据 |
|---|-----------|-----------|-------------------|
| 1 | 用户旅程完整 | 所有关键路径端到端工作 | Reality Checker 截图 |
| 2 | 跨设备一致性 | 桌面 + 平板 + 移动全部正常工作 | 响应式截图 |
| 3 | 性能已认证 | P95 < 200ms，LCP < 2.5s，正常运行时间 > 99.9% | Performance Benchmarker 报告 |
| 4 | 安全性已验证 | 零严重漏洞 | 安全扫描 + 合规报告 |
| 5 | 合规已认证 | 所有监管要求已满足 | Legal Compliance Checker 报告 |
| 6 | 规格合规性 | 100% 的规格需求已实现 | 逐点验证 |
| 7 | 基础设施就绪 | 生产环境已验证 | Infrastructure Maintainer 报告 |

## 关卡决策

**唯一权威**：Reality Checker

### 如果就绪（推进到第 5 阶段）：
```markdown
## 第 4 阶段 → 第 5 阶段交接包

### 给发布团队：
- Reality Checker 认证报告
- 性能认证
- 合规认证
- 基础设施就绪报告
- 已知限制（如有）

### 给 Growth Hacker：
- 产品已准备好面向用户
- 用于营销消息的功能列表
- 用于可信度的性能数据

### 给 DevOps Automator：
- 生产部署已批准
- 蓝绿部署计划
- 回滚程序已确认
```

### 如果需要改进（返回到第 3 阶段）：
```markdown
## 第 4 阶段 → 第 3 阶段返回包

### 修复列表（来自 Reality Checker）：
1. [严重问题 1]：[描述 + 证据 + 修复说明]
2. [严重问题 2]：[描述 + 证据 + 修复说明]
3. [高优先级问题 1]：[描述 + 证据 + 修复说明]
...

### 流程：
- 问题进入开发↔QA 循环（第 3 阶段机制）
- 每个修复必须通过 Evidence Collector QA
- 当所有修复完成 → 返回到第 4 阶段步骤 3
- Reality Checker 使用更新后的证据重新评估

### 预期：2-3 个修订周期是正常的
```

### 如果未就绪（返回到第 1/2 阶段）：
```markdown

1. [根本问题]：[为什么无法在第 3 阶段修复]
2. [结构问题]：[需要在架构层面更改什么]

### 建议操作：
- [ ] 修订系统架构（第 1 阶段）
- [ ] 重建基础（第 2 阶段）
- [ ] 缩减范围并重新定义（第 1 阶段）

### 需要 Studio Producer 决策
```

---

*当 Reality Checker 以压倒性证据发出就绪判定时，第 4 阶段即告完成。需要改进是预期的首次通过结果 — 这意味着系统正在工作，但需要打磨。*
